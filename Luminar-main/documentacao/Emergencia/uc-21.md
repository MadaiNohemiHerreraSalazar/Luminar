# UC-13 — Executar Protocolo de Alerta e Evidência (Sistêmico)

**Produto:** Luminar  
**Objetivo:** Gerenciar de forma automatizada o processamento de dados de emergência, garantindo a entrega de alertas à rede de apoio e a integridade da gravação de áudio como prova pericial.

## Atores

- **Sistema (Servidor de Backend / Worker de Emergência)**
- **API de SMS (Ex: Twilio / Zenvia)**
- **Storage Cloud (Servidor de Arquivos Seguro)**

## Regras de Negócio Aplicadas

### RN-01 — Fragmentação de Áudio (Chunking)
- O áudio gravado não deve ser salvo como um único arquivo ao final. O sistema deve fragmentar a gravação em blocos de 30 segundos e enviá-los imediatamente para a nuvem. Isso garante que, se o celular for quebrado ou desligado, os minutos anteriores já estejam salvos no servidor.

### RN-02 — Inteligência de Conectividade
- Caso a conexão de dados caia, o sistema deve enfileirar os pacotes de áudio e tentar o reenvio automático assim que detectar qualquer sinal (Wi-Fi ou 4G), priorizando o tráfego de emergência sobre qualquer outra função do app.

### RN-03 — Conteúdo Dinâmico do SMS
- O SMS deve ser estruturado para ocupar o menor espaço possível (evitando múltiplas cobranças/atrasos) e conter obrigatoriamente:
    - Identificação da usuária.
    - Link direto para o mapa de monitoramento.
    - Texto de alerta: "EMERGÊNCIA LUMINAR: [Nome] acionou o pânico. Acompanhe aqui: [Link]".

### RN-04 — Registro de Log Pericial (Audit Log)
- Todas as ações executadas pelo sistema durante o modo de pânico devem ser registradas com *timestamp* de alta precisão (milissegundos) para servir como evidência legal posterior.

## Caso de Uso: UC-13

### Pré-condições

- O Modo de Emergência foi disparado pela usuária (UC-12).
- O sistema possui tokens ativos para uso das APIs de comunicação.

### Gatilho

- Recebimento do sinal de ativação do Modo de Pânico pelo Backend.

### Fluxo Principal (Sucesso)

1. O sistema valida as credenciais da usuária e recupera a lista de **Contatos de Emergência** do banco de dados.
2. O sistema gera uma URL única e temporária de monitoramento (similar ao UC-11, mas com nível de alerta alto).
3. O sistema dispara as requisições para o **Gateway de SMS** para todos os contatos da lista.
4. O servidor abre um *socket* de comunicação exclusivo para receber o streaming de áudio do dispositivo.
5. O sistema processa os pacotes de áudio recebidos, criptografa-os e armazena-os em um diretório de segurança máxima.
6. O sistema monitora a pulsação (heartbeat) do GPS da usuária. Se a localização não mudar por mais de 5 minutos em modo de pânico, o sistema envia um segundo SMS de reforço aos contatos.
7. Ao receber o sinal de desativação (via PIN correto), o sistema consolida os arquivos de áudio, encerra o link de monitoramento e gera um relatório resumido do incidente.

### Pós-condições

- Os contatos foram notificados com sucesso.
- O material probatório (áudio e trilha GPS) está disponível para a usuária (ou autoridades) mediante autenticação.

## Cenários de Validação

### CT-01 — Falha no Envio de um dos Contatos
**Dado** que um dos contatos de confiança está com o número inválido ou fora de área  
**Quando** o Gateway de SMS retorna erro  
**Então** o sistema deve tentar o reenvio imediato por mais 2 vezes e registrar a falha no log de auditoria para informar a usuária posteriormente.

### CT-02 — Integridade do Áudio pós-destruição do aparelho
**Dado** que o celular da usuária foi destruído 2 minutos após o acionamento  
**Quando** o servidor para de receber os pacotes de áudio  
**Então** o sistema deve garantir que os 120 segundos anteriores de gravação estejam íntegros e disponíveis no Storage Cloud.

### CT-03 — Consumo de Créditos de SMS
**Dado** que o saldo de SMS do sistema está baixo  
**Quando** ocorre um acionamento de pânico  
**Então** o sistema deve disparar um alerta crítico para os administradores e utilizar canais alternativos (Push Notification/E-mail) como redundância imediata.

### CT-04 — Mudança de fuso horário/horário de verão
**Dado** que o incidente ocorre durante uma mudança de horário  
**Quando** os registros são salvos  
**Então** o sistema deve utilizar o formato **UTC** (Coordinated Universal Time) para todos os logs internos, convertendo para o horário local apenas na visualização da usuária.

### CT-05 — Finalização da Sessão por Inatividade
**Dado** que o sistema não recebe sinais de GPS ou áudio por mais de 6 horas em modo de pânico  
**Quando** o tempo limite é atingido  
**Então** o sistema deve encerrar a sessão de emergência automaticamente para preservar a privacidade e evitar vazamento de dados de uma sessão esquecida.
